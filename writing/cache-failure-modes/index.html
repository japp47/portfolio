Five lines of cache-aside, and the three ways they fall over

A cache fixes latency. It also adds three new ways for a system to fall over.

21 Feb 2026 · 10 min · caching · redis · interactive

Almost every service has these five lines somewhere:

def get(key):
    if (value := cache.get(key)) is not None:
        return value
    value = db.query(key)
    cache.set(key, value, ttl=300)
    return value

Nothing in them is wrong. They are cache-aside, the most common caching pattern there is, and they work beautifully right up until traffic stops being polite. They quietly assume three things:

  1. The keys people ask for exist. Otherwise every request is a miss.
  2. Keys expire quietly. Otherwise an expiry is an event.
  3. Load spreads evenly across keys. Otherwise one key is everyone's problem.

Each assumption breaks at scale, each break has a name, and each fix costs something.

1. Keys that don't exist: cache penetration

Ask for user:8f3a…, an ID that was never created. The cache misses, because there was never anything to cache. The database misses too. Nothing gets written back, so the next request for the same key does exactly the same thing. Send a few thousand of those a second from rotating addresses and every one of them lands on the database.

It is not only attackers. A client that retries lookups for deleted records, or a scraper walking an ID range, does the same thing by accident. Per-IP rate limiting helps with the first and does nothing about a botnet; it is a different layer, not a fix.

Cheap fixes first

  • Cache the miss. Store "not found" with a short TTL, say 30 seconds. Repeated requests for the same missing key now stop at the cache. It does nothing against an attacker who never asks for the same key twice.
  • Validate the shape. If IDs are UUIDs or carry a checksum, a malformed one can be rejected before any lookup at all.

The real fix: a Bloom filter

A Bloom filter answers one question — could this key ever have been added? — with a few hash computations and very little memory, without touching the database. It is an array of bits and a few hash functions. Adding a key sets the bits its hashes point to. Checking a key looks at the same bits: if any of them is still 0, the key was definitely never added. If they are all 1, it maybe was, because other keys may have set those bits.

That asymmetry is the whole point. A false positive costs one wasted database lookup. A false negative would turn a real user away. Bloom filters never give a false negative, as long as every key is added.

And they are small. At a 1% false-positive rate a filter needs about 9.6 bits per key and 7 hash functions, so ten million keys fit in roughly 12 MB. Redis ships one (BF.RESERVE, BF.ADD, BF.EXISTS); Guava has one for the JVM.

The catch is in "as long as every key is added". Add to the filter before the new row becomes visible, not after. A missed add is a real user getting a 404.

The other costs: a plain Bloom filter can't delete, because a bit may be shared, so deleted keys linger as false positives until you rebuild. Counting Bloom filters and cuckoo filters support deletes, at more memory per key.

2. Keys that expire loudly: the stampede

A key everyone reads — a trending post, a flash-sale price, the home page config — expires. In the hundred milliseconds it takes to rebuild, every request misses and every request decides, on its own, to query the database. Each of those queries makes the next one slower, so the rebuild takes longer, so more requests miss.

The striking number in the unprotected run is the last one. The cache is full again at 0.3 s, but the database is still working through the pile-up until 1.4 s. Every query sent during those first hundred milliseconds has to finish, whether anyone still needs its answer or not.

Let one request rebuild

Whoever misses first takes a lock and rebuilds; everyone else waits briefly and reads the fresh value. In Redis the lock is one command: 

SET lock:home_feed <random-token> NX PX 5000   # only if absent, expires in 5 s

You don't need Redlock or ZooKeeper for this. The lock is there for efficiency, not correctness: if it fails and two requests rebuild, you wasted one query and nobody saw wrong data. Martin Kleppmann draws exactly that line in How to do distributed locking, and it decides how much machinery a lock deserves. Inside one process, Go's singleflight does the same job before the request even reaches Redis.

Or don't make anyone wait

Store a soft expiry inside the value and a longer TTL on the key. Past the soft expiry, serve the old value and let one request refresh it in the background. Users see data a few seconds older; nobody waits and the database sees one query. For feeds, counters and dashboards that is the right trade. For a bank balance it is not.

Or refresh before it expires

Probabilistic early expiration (Vattani et al., VLDB 2015) has each reader roll a die that gets more likely to come up "refresh" as the expiry approaches, weighted by how long a rebuild takes. One reader refreshes early; the key never actually expires under load. 

# delta: how long a rebuild takes; beta: 1.0 by default, higher refreshes earlier
if now - delta * beta * log(random()) >= expiry:
    rebuild()

A cousin of the stampede: thousands of keys written at the same moment, by a deploy warming the cache or a nightly batch job, all expire at the same moment too. Add jitter to every TTL — 300 seconds plus a random 0 to 30 — and the expiries spread out on their own.

3. One key everyone wants: the hot key

A cache cluster spreads keys across nodes by hashing them. That spreads keys, not traffic. If one key takes half your reads, the node that owns it takes half your reads, and it saturates while the rest of the cluster idles. The database is fine; the cache is the bottleneck.

  • Keep a local copy first. An in-process cache with a one-second TTL turns thousands of reads a second from each app server into one. It is usually the biggest win, and the price is up to a second of staleness.
  • Then split the key. Store N copies under suffixed keys that hash to different nodes, and read a random one. The price: every write and invalidation has to touch all N, and for a moment they can disagree.
  • Find it before it finds you. redis-cli --hotkeys lists the hottest keys, once the eviction policy is one of the LFU ones (allkeys-lfu).

All of it, in order

Put together, a read path that survives all three looks like this:

failure the assumption that broke fix, and what it costs
Penetration The keys people ask for exist Bloom filter: memory, keeping it in sync, no deletes
Stampede Expiry is quiet One rebuild, stale reads or early refresh: brief waits or older data
Mass expiry Keys expire independently TTL jitter: slightly less predictable expiry
Hot key Traffic spreads evenly Local cache, key copies: more memory, wider invalidation
None of these are bugs in the five lines. They are what happens when the five lines meet scale, or someone hostile. A cache isn't only a speed layer; it is part of how the system stays up.

The stampede simulator is a toy model: each query takes 100 ms on an idle database and slows in proportion to how many are running. Real databases degrade less politely. Further reading: Kleppmann on distributed locks ↗ and Optimal Probabilistic Cache Stampede Prevention ↗.
