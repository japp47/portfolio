What the Postgres planner is actually deciding

It doesn't run your SQL. It prices every way it could, and runs the cheapest one it can see.

18 Aug 2026 · 11 min · postgres · performance · interactive

The same query takes four milliseconds on Monday and forty seconds on Friday. Nobody changed the SQL. Nobody dropped an index. What changed is the plan — and the plan is a decision PostgreSQL makes fresh, every time, from numbers that can quietly go stale.

SQL says what you want, never how to get it. Between your query and your data sits the planner, and most "Postgres is slow" stories are really stories about what it decided and why.

From text to rows

Every query passes through four stages. Only one of them makes choices.

EXPLAIN shows you the planner's answer. EXPLAIN ANALYZE also runs the executor and shows how that answer turned out.

What it is choosing between

For every table, a way to read it. For every join, a method and an order. The options multiply quickly — past twelve tables in one query (geqo_threshold), Postgres stops searching exhaustively and switches to a genetic search.

reading a table how it works wins when
Seq Scan Read every page in order, check every row A large share of the table matches
Index Scan Walk the index, then fetch each matching row from the table Few rows match, or rows sit in index order
Index Only Scan Answer from the index alone, never touching the table The index has every column the query needs
Bitmap Heap Scan Collect matches from the index, sort them by page, read each page once The middle ground, or combining two indexes with AND / OR
joining two how it works wins when
Nested Loop For each row on one side, look up its matches on the other One side is small and the other has an index
Hash Join Build a hash table from one side, probe it with the other Big, unsorted inputs joined on equality
Merge Join Walk two sorted inputs side by side Both sides are already sorted, often by an index

Cost is arithmetic

Each candidate plan gets a cost: a number in made-up units where reading one page in sequence costs 1. The prices live in postgresql.conf: 

seq_page_cost        = 1.0     # read the next page
random_page_cost     = 4.0     # jump to some other page
cpu_tuple_cost       = 0.01    # handle one row
cpu_index_tuple_cost = 0.005   # handle one index entry
cpu_operator_cost    = 0.0025  # evaluate one operator, like >=

Price a sequential scan of a million-row table stored on 10,000 pages:

10,000 pages      × 1.0     = 10,000
1,000,000 rows    × 0.01    = 10,000
1,000,000 checks  × 0.0025  =  2,500
                              ------
                              22,500   # EXPLAIN prints cost=0.00..22500.00

An index scan pays random_page_cost for nearly every row it fetches, because each one can live on a different page. That makes it very cheap for ten rows and very expensive for half the table. Somewhere in between, the lines cross.

random_page_cost = 4 was set for spinning disks. On SSDs many teams lower it toward 1.1, which makes index scans look cheaper and moves every crossover.

Play the planner

Here is that cost model, simplified, for SELECT * FROM orders WHERE created_at >= $1 on the same million-row table, with an index on created_at. Drag the slider, or the chart itself, to change how many rows the planner expects to match.

Three things worth noticing:

  • An index is not always faster. Past a point, jumping around the table one row at a time costs more than reading all of it in order. When the planner ignores your index on a broad query, it is usually right.
  • Bitmap scans are the compromise. They use the index to find rows but read pages in physical order, which is why they show up so often on mid-sized results.
  • Physical order changes everything. Switch on table stored in date order. In an append-only table, rows arrive in created_at order, so the index and the table agree and an index scan stays cheap far longer. The same index on customer_id, scattered everywhere, gives up much sooner.

The estimate is the weak link

Every cost above multiplies by one input: how many rows will match. The planner can't count them without running the query, so it estimates them from statistics that ANALYZE gathers for each column — the share of nulls, the number of distinct values, the most common values and their frequencies, a histogram of the rest, and how closely the column follows the table's physical order. 

SELECT null_frac, n_distinct, most_common_vals, most_common_freqs, correlation
FROM pg_stats
WHERE tablename = 'orders' AND attname = 'status';

ANALYZE reads a sample of 300 × default_statistics_target rows — 30,000 by default — however large the table. Autovacuum re-runs it once 50 rows plus 10% of the table have changed. On a hundred-million-row table, that is ten million changes before the statistics catch up.

Now turn on statistics are stale in the demo above. The planner believes 10 rows will match and picks an index scan; 300,000 do. On a single table that costs a few times the work. In a join, it compounds.

Reading EXPLAIN ANALYZE

A queue: orders go from pending to done. When statistics were last gathered, pending was rare. Then a downstream service was down for an afternoon, and the backlog grew: 

EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, c.email FROM orders o JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'pending';

Nested Loop  (cost=0.85..152.40 rows=12 width=40) (actual time=0.061..2841.772 rows=48210 loops=1)
  Buffers: shared hit=193020 read=41877
  ->  Index Scan using orders_status_idx on orders o  (cost=0.42..48.10 rows=12 width=16)
        (actual time=0.031..61.204 rows=48210 loops=1)
        Index Cond: (status = 'pending'::text)
  ->  Index Scan using customers_pkey on customers c  (cost=0.42..8.44 rows=1 width=32)
        (actual time=0.052..0.055 rows=1 loops=48210)
        Index Cond: (id = o.customer_id)

An illustrative plan, wrapped and trimmed for reading.

Read it from the innermost lines out, comparing rows= with actual rows= on each:

  1. The orders scan expected 12 rows and got 48,210 — four thousand times off. It is the first line where estimate and reality part ways, so it is where the plan went wrong.
  2. For 12 rows, a nested loop was the right call: twelve primary-key lookups. For 48,210 it means 48,210 separate lookups, which is what loops=48210 on the customers scan says. A hash join would have read customers once.
  3. Numbers on a looped line are per loop. 0.055 ms looks harmless until you multiply it by 48,210.
  4. Everything above the first bad estimate is built on it. Don't tune the join. Fix the number.

Here the immediate fix is ANALYZE orders;. The lasting one is making sure it runs often enough on a table whose shape changes by the hour: 

ALTER TABLE orders SET (autovacuum_analyze_scale_factor = 0.01);  -- 1%, not 10%

And BUFFERS says where the time went: shared hit pages came from Postgres's own cache, read pages had to come from the operating system or the disk. Since PostgreSQL 18, EXPLAIN ANALYZE includes it by default.

Design so the planner can win

Postgres has no built-in query hints. (The pg_hint_plan extension adds them, at the price of maintaining plans by hand.) What you can do is give the planner true numbers and good options:

  • Keep statistics honest. Run ANALYZE after bulk loads and large deletes. Lower the analyze scale factor on big tables that change fast, and raise the statistics target on skewed columns: ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000;
  • Tell it which columns move together. The planner assumes conditions are independent, so city = 'Bengaluru' AND state = 'Karnataka' multiplies two selectivities and underestimates badly. CREATE STATISTICS addresses_geo (dependencies) ON city, state FROM addresses; fixes it.
  • Partition by time when queries mostly touch recent data. A query for last week then plans and scans only last week's partitions.
  • Give sorts and hashes room, carefully. Sort Method: external merge or a hash with Batches above 1 means it ran out of work_mem and spilled to disk. But that limit applies per sort or hash, per query, per connection; Zerodha's engineering team has written about how fast it multiplies. Raise it with SET LOCAL for the queries that need it, not for the whole server.
  • Make the plan part of review. A change that puts a query on a hot path ships with its EXPLAIN ANALYZE, run against production-sized data.
The planner isn't guessing, and it isn't magic. It is doing arithmetic on estimates. When a query is slow, ask where the estimate first went wrong before asking which index is missing.
