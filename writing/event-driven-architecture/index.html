Event-driven architecture, and the part the diagrams leave out

Every explainer shows one arrow becoming five. The hard problems start one step earlier.

25 Jun 2026 · 9 min · kafka · postgres · distributed systems

You post a photo. In the next second it has to reach your followers' feeds, fire notifications, get indexed for search, feed a recommendation model and land in analytics. Every article about this draws the same picture: one service publishes an event, five services listen. It is a good picture and it is true.

It is also the easy half. The four things that actually bite — losing an event you thought you published, handling the same event twice, getting two events in the wrong order, and finding out which consumer dropped the ball — are all invisible in that drawing. This is about those.

First, the picture everyone draws

The obvious design is a chain. The photo service calls the notification service, which calls search, which calls analytics. It works until it doesn't.

Every link adds its latency to the user's wait, and every link can fail the whole request.

The upload is still synchronous: save the photo, return success. Everything after it is not.

What the fan-out actually buys

Three things, and it is worth being precise about which, because people often claim a fourth that isn't true.

  • Failure stops spreading. Search falling over no longer fails an upload, because the upload never waited for search.
  • You scale the part that's busy. A celebrity posts and notifications get hammered; you add notification consumers without touching anything else.
  • A new feature is a new listener. Adding a moderation service means subscribing to an event that already exists. No pull request against the photo service.

What it does not buy you is less work or fewer failures. The same five jobs still run and any of them can still fail — you have just stopped making the user wait to find out.

The write that isn't in the picture

Look again at the fan-out diagram. The photo service does two things: it saves the photo to its database, and it publishes an event to the broker. Two systems, two writes, and no transaction spanning both.

So what happens if the process dies between them?

Publishing first instead does not help: then you can announce a photo that was never saved.

The event is now as durable as the photo, because it is stored by the same commit.

This is the outbox pattern, and it is the single most useful thing to know about event-driven systems. The event goes into an ordinary table in the same database, inside the same transaction as the business write: 

begin;

insert into photos (id, user_id, url)
values ($1, $2, $3);

insert into outbox (id, topic, payload)
values ($4, 'photo.posted', $5);

commit;   -- both, or neither

A separate relay then reads unsent rows, publishes them, and marks them sent. Every failure now has an answer. The relay crashes before publishing? The row is unsent; it goes next pass. It publishes but dies before marking sent? It publishes again — which is fine, because of the next section.

If you take one thing from this: you cannot write to a database and a broker atomically, so stop trying. Write to one, and let something else move it to the other.

Delivered at least once, which means twice

Brokers promise at-least-once delivery. Exactly-once is sold hard and is mostly a careful arrangement of at-least-once plus deduplication; treating it as a primitive will hurt you. So assume every consumer will see some events twice, and make that boring rather than dangerous.

The trick is that the consumer records what it has already done, keyed by the event's id, in the same transaction as its own work: 

-- in the notification service's own database
insert into handled (event_id)
values ($1)
on conflict (event_id) do nothing;

-- 0 rows means we have seen this one before: stop here,
-- ack the message, and send nothing.

Note where that table lives: in the consumer's database, not the producer's. Each consumer is responsible for its own duplicates, because each one has a different idea of what "already done" means. Sending a push notification twice is bad. Incrementing an analytics counter twice is bad. Setting a search index entry twice is harmless, so search may not need the table at all.

Order holds only where you ask for it

A broker gives you ordering within a partition, not across a topic. If photo.posted and photo.deleted for the same photo land on different partitions, a consumer can be told about the deletion first and then re-create what it just removed.

The fix is to partition by the thing whose order matters — the photo id, or the user id — so every event about one entity travels the same lane. It costs you something real: one hot key, say a celebrity account, now has a single consumer working through it while others idle.

Ordering problems are rarely about the broker. I hit the same shape of bug in a sync protocol I built, where Postgres handed out sequence numbers before the transactions committed, so two writes became visible out of order and a client stepped straight past one. Different system, identical lesson: a number you were given is not a promise about when anyone else will see it.

What it costs

  • Eventual consistency, out loud. The photo is up before the follower count moves. That is a product decision as much as a technical one, and someone has to decide what the UI shows in the gap.
  • Debugging becomes tracing. There is no single stack to read. Without a correlation id carried on every event and logged by every consumer, "it didn't show up" is close to unanswerable.
  • The broker is now critical infrastructure. You have swapped several direct dependencies for one shared one that needs its own monitoring, retention policy and dead-letter handling.
  • Schemas get harder. Five consumers read your event, you do not know who, and renaming a field breaks them silently. Events need versioning in a way function arguments don't.

When not to reach for it

If the caller needs the answer, this is the wrong tool. A payment authorisation, a login, a uniqueness check at sign-up — these are synchronous by nature, and routing them through a broker just means reinventing request and response with worse tooling.

The honest test is the one the fan-out diagram is really showing: does the user need this to have happened before they see success? If yes, call it. If no, publish an event and let it happen when it happens.

Two of the ideas here show up in the projects on this site: the ordering bug in the 99ile sync protocol, and the question of what to write before you commit to anything in the Local LLM Gateway. If you have hit a variant of either, I would like to hear about it.
