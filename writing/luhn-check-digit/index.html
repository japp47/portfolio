How credit cards catch typos: the Luhn algorithm

Every card number ends in a digit whose only job is to catch your mistakes. Here is how it works, and what it misses.

13 Feb 2026 · 8 min · payments · algorithms · interactive

Ever wondered how a payment form knows you typed your card number wrong before anything reaches a server? There is a 70-year-old algorithm hidden in every card number, and it runs in your browser in a few microseconds.

Here is how it works, what it catches, what it doesn't, and why it matters for a payment integration.

The anatomy of a card number

Take this Mastercard test number. It isn't random; every part has a job.

The last digit carries no information about you at all. It is there purely so that a mistake in any of the others can be spotted.

How the Luhn algorithm works

Hans Peter Luhn, a scientist at IBM, filed the patent in 1954. The whole thing is four steps:

  1. Remove spaces and dashes, keep the digits.
  2. Starting from the right, double every second digit.
  3. If doubling gives a number above 9, subtract 9. (14 becomes 5, the same as 1 + 4.)
  4. Add everything up. If the total ends in 0, the number is valid.

Try it below. Each box shows a digit, whether it was doubled, and what it adds to the total.

Why the doubling trick works

Doubling-and-subtracting-9 turns the digits 0 to 9 into 0, 2, 4, 6, 8, 1, 3, 5, 7, 9: every digit still, just shuffled. So changing any one digit, doubled or not, moves the total by somewhere between 1 and 9. That can never land on another multiple of 10, which is why a single wrong digit is always caught.

Swapping two neighbours usually changes the total too, because one of them was doubled and the other wasn't. 13 ↔ 31 and 56 ↔ 65 are both caught. The one exception is 09 ↔ 90: 0 doubled is 0, 9 doubled is 18 → 9, so the pair adds 9 whichever way round it is.

I didn't want to repeat the percentages that float around, so I measured them: 3,000 random valid 16-digit numbers, and every possible typo of each kind.

typo example Luhn catches
One digit wrong 5425 → 5465 100%, always
Neighbours swapped 13 → 31 98%; only 09 ↔ 90 slips through
Twin digits wrong 11 → 55 93%; misses 22 ↔ 55, 33 ↔ 66, 44 ↔ 77
Swap across one 123 → 321 0%, never

That last row is the blind spot most write-ups get wrong. Digits two apart are either both doubled or both not, so swapping them can't change the total. Luhn misses every one of those.

Better schemes exist (Verhoeff and Damm also use a single check digit and catch every neighbour swap), but nobody switched. Luhn is written into the card standard and into every card already in a wallet. Once a format is everywhere, "good enough and universal" beats "better and new".

A production-ready check

In a real form, Luhn is one part of a short function:

function luhnSum(digits: string): number {
  let sum = 0;
  for (let i = 0; i < digits.length; i++) {
    let d = Number(digits[digits.length - 1 - i]);  // walk from the right
    if (i % 2 === 1) {
      d *= 2;
      if (d > 9) d -= 9;
    }
    sum += d;
  }
  return sum;
}

function checkCard(input: string) {
  const digits = input.replace(/\D/g, '');             // strip spaces and dashes
  if (digits.length < 13 || digits.length > 19) return { ok: false, reason: 'length' };
  if (luhnSum(digits) % 10 !== 0) return { ok: false, reason: 'typo' };
  return { ok: true, last4: digits.slice(-4) };         // only ever show or log these
}
  • Strip non-digits so people can paste numbers with spaces or dashes.
  • Check the length: card numbers are 13 to 19 digits.
  • Show only the last four once it's entered, and never log the full number.
  • Use brand detection for the logo, not to reject. Ranges change: Mastercard added a whole new 2-series in 2017, and issuer prefixes grew from 6 to 8 digits in 2022. A form that refuses numbers it doesn't recognise turns away real customers.

It runs in linear time, in microseconds, with no dependencies.

Generating valid test numbers

Because the last digit is just arithmetic, you can make any number pass: pick the first 15 digits, then compute the 16th. 

function checkDigit(body: string): number {
  // pretend the check digit is 0, then see how far the total is from a multiple of 10
  return (10 - (luhnSum(body + '0') % 10)) % 10;
}

checkDigit('411111111111111');  // 1  →  4111 1111 1111 1111

That is handy for UI tests and automation without touching real card data. For a payment gateway's sandbox, use the provider's own published test numbers instead; a generated number passes Luhn, but the sandbox only recognises its own.

What Luhn doesn't validate

Luhn tells you a number was probably typed correctly. That's all.

it does it doesn't
Catch accidental typos Check that the card exists
Catch every single-digit error Check that it's active or not expired
Work offline, with no API call Check the CVV or billing address
Run instantly Stop fraud of any kind

Think of Luhn as the first line of defence, not the only one.

Luhn or the payment API?

Both, at different steps. Each step of a payment knows more, and costs more to ask:

  • Use Luhn in the browser for instant feedback while the person is still typing.
  • Use the payment API to actually charge the card, check the CVV and address, and run fraud checks. Only the issuer knows whether the card is real.
  • Best of both: Luhn on the front end, the processor's validation behind it. With the provider's hosted card fields, the number goes from the browser straight to them, and your servers only ever see a token, which also keeps them out of most of the PCI DSS scope.

Real-world impact

  • Better experience. The mistake is flagged while the person is still typing.
  • Fewer wasted calls. A rough example: 10,000 payment attempts a month, 5% with a typo, is 500 calls that could only ever be declined. At $0.10 each that's $50 a month, before counting the support tickets.
  • Cleaner signals. Fewer pointless declines means less noise for the fraud systems watching your traffic.
The bottom line: a 70-year-old checksum, about 15 lines of code, that still checks every card number typed into every checkout. Fast, free, no dependencies. Just know which mistakes it can't see.
