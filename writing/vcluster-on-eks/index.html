Fifty EKS clusters, or one: what vCluster actually shares

The control plane was never the expensive part. It was everything we copied around it.

1 May 2026 · 10 min · kubernetes · eks · aws

A QA engineer asks for a test environment. The platform team provisions a fresh EKS cluster: control plane, node group, load balancer, DNS, monitoring agents. Forty-five minutes later they have somewhere to deploy. Multiply by a few dozen teams and you have a full-time job maintaining environments that are idle most of the day.

The obvious reading is that Kubernetes clusters are slow to create. The more useful reading is that almost nothing in those forty-five minutes was about isolation. It was about copying the same plumbing into yet another account-shaped hole.

What a cluster per team actually costs

Isolation is the thing you wanted. Here is what you paid for alongside it, fifty times over.

Each environment also idles most of the day, while its node group keeps a floor of capacity running.

A virtual cluster is a control plane running as pods — API server, controller manager and its own datastore — inside a namespace on the host.

A virtual cluster is not a namespace with better manners. Your team gets a real API server, so you can install CRDs, make cluster roles and run operators — none of which a shared namespace allows.

The part that makes it work: syncing in both directions

A virtual cluster on its own would be an island. What makes it useful on EKS is that specific resources cross the boundary, and the direction matters.

  • Host → virtual. The ingress class and storage class are pushed down, so a developer inside the virtual cluster can ask for alb or a gp3 volume as if they had installed those controllers themselves.
  • Virtual → host. Ingress objects are pulled up, so the one ALB controller running on the host sees them and acts on them. 
sync:
  fromHost:
    ingressClasses: { enabled: true }   # the ALB class, usable inside
    storageClasses: { enabled: true }   # gp3, usable inside
  toHost:
    ingresses: { enabled: true }        # rules bubble up to the real ALB

That second direction is the one that saves the money. An Ingress created by a QA engineer inside their own cluster turns into a rule on a load balancer they cannot see and do not pay for.

The grouping annotation is what lets separate Ingress objects share one load balancer instead of creating one each.

Set the group once on the ingress class and every environment lands on the same ALB:

apiVersion: eks.amazonaws.com/v1
kind: IngressClassParams
metadata:
  name: alb
spec:
  scheme: internet-facing
  group:
    name: vcluster        # 50 ingresses, 1 load balancer

The numbers

Worth reading as orders of magnitude rather than precise figures — the cost side depends entirely on instance types, region and how long environments actually live.

Compute pricing on-demand Spot, up to 70% less

The hours matter more than the dollars. Forty-five minutes of waiting is not just forty-five minutes; it is the reason a QA engineer batches up changes instead of testing one at a time, and the reason environments get kept alive “just in case” rather than deleted. Making creation cheap changes the behaviour, not only the bill.

Where logical isolation stops being enough

This is the part a vendor page will not dwell on. Virtual clusters give you logical isolation, not infrastructure isolation, and the difference is not academic.

  • The nodes are shared. A test that eats memory is eating it from a pool other teams are scheduled on. Resource quotas and limit ranges are not optional here the way they arguably are on a dedicated cluster.
  • The kernel is shared. Anything that holds for containers on one host holds here. A workload that needs a hard security boundary needs a different answer.
  • The host's failures are everyone's. You traded fifty small blast radii for one large one. Upgrading the host cluster is now an event, not a Tuesday.
  • Debugging crosses a seam. A resource exists twice — inside the virtual cluster and, renamed, in a host namespace. When something does not appear, you need to know which side to look at.

When to reach for it

The pattern fits when environments are many, similar and short-lived: review apps, QA environments, per-branch previews, training sandboxes. That is exactly the shape where a dedicated cluster is nearly all overhead.

It does not fit when you need a hard compliance boundary, when the workload wants specific hardware and its own node pool, or when you only have one or two long-lived clusters — in which case this is a layer of indirection buying you nothing.

The underlying question is the same one worth asking of any multi-tenancy decision: what exactly are you isolating, and from whom? If the answer is "teams from each other's mistakes", logical isolation is usually enough. If the answer involves the word "auditor", it is not.
