01 / what it is

Your own models, on your own machine.

A small Fastify server in front of Ollama, plus a terminal app and a browser chat page. It keeps your history, picks a model that fits your machine's memory, explains problems in plain words, and backs your chats up. No Docker, no database to set up.

The engineering interest is not the model part — it is everything around it. There is one GPU, one Ollama, and a stream that can die halfway through. The gateway's job is to make sure that when something goes wrong, the database is not left holding half an answer.

Target hardware is a MacBook Air M4 with 16 GB, and every performance claim in the repo is measured there. That one machine is why admission control exists at all: a second concurrent generation does not halve throughput, it pushes the model out of unified memory and falls off a cliff. So the default is one generation at a time, with a bounded queue in front of it.

The second rule is that the run mode is chosen only by configuration. A DATABASE_URL means server mode on PostgreSQL and Redis; without one it is single-user mode on SQLite. Same code, same tests, two deployments.

02 / architecture

Three ways in, one way down.

Every request arrives through the same hooks whether it came from the CLI, the browser page or a raw HTTP client. Point at a box to follow what it touches.

That seam was not designed up front; it was forced. Three Postgres-only features had to be rewritten for SQLite: percentile_cont for the stats endpoint, reimplemented exactly in src/lib/stats.ts; FOR SHARE row locks when forking a conversation, which became a transaction; and make_interval in the lease. The same integration suite runs against both, and there is a test file that exists purely for the cases where two adapters tend to drift apart.

03 / data model

Five tables, mirrored twice.

Drizzle, with the Postgres and SQLite schemas written table for table against each other. The SQLite differences are deliberate and commented: ids are text UUIDs made in application code, timestamps are integer milliseconds, and the message sequence is the autoincrement primary key.

Three choices in there I would defend. updated_at is declared with millisecond precision because it is the keyset pagination cursor, paired with the id as a tie-breaker so equal timestamps are never skipped — and a JavaScript date and JSON only carry milliseconds, so the column matches what can round-trip. generations.message_id has no foreign key, so the operational record of what happened survives the message being deleted. And generations holds one row per attempt, not per success: queue wait, time to first token, token counts, status and error code. That is the dataset the stats endpoint reads to give p50 and p95 per model, for the calling user only.

04 / two guards

A lease and a semaphore are not the same thing.

They look alike — both stop work from happening twice. But they protect different things, fail differently, and only one of them needs to survive a crash.

the lease the semaphore
protects one conversation's correctness the GPU
lives in the database, per conversation memory, per process
turns away with 409 conversation_busy 503 server_busy, retry-after 5
survives a crash yes — it expires no, and it needn't

The lease is a single atomic compare-and-set, so two requests racing for the same conversation cannot both win: 

update conversations
   set lease_until = now() + make_interval(secs => $2)
 where id = $1
   and (lease_until is null or lease_until < now())
returning id

Because it expires — three minutes by default — a process that dies mid-generation does not leave a conversation locked forever.

The semaphore is about forty lines, and two details matter. Releasing hands the slot directly to the next waiter without touching the active count, so there is no window where a freed slot could be claimed twice. And the release function is idempotent, so a double release cannot inflate capacity: 

private makeRelease() {
  let released = false;
  return () => {
    if (released) return;
    released = true;
    const next = this.waiters.shift();
    if (next) next();       // hand the slot over directly
    else this.active--;
  };
}

A request aborted while queued splices itself out of the waiter list, rather than being granted a slot nobody is waiting for any more.

05 / the order of operations

Open the stream before writing anything.

The obvious order is: save the user's message, return 200, then call the model. It is also wrong — and you only find out when Ollama is stopped.

Two commitments were made before the one thing that could fail was tried: a database write, and a 200.

The cost is honest and documented: a cold first answer starts about two seconds later, because opening the stream waits for the model to load.

And when it dies halfway

If the stream fails after some text has arrived, the accumulated text is saved with status partial, the error code goes into the generations row, and the client still gets its closing events. Error-status messages are filtered out of future context, so a failed answer never poisons the next one. A client that simply disconnects gets no error event at all.

Provider failures are a closed set — ollama_unavailable, model_not_installed, model_too_large, model_stopped, provider_error — classified where Ollama's responses are parsed and mapped to HTTP one layer up. The detail string is marked for logs only: never shown to users.

One gap is still open, and it is in the repo's own notes: a hard crash, as opposed to a dropped connection, still loses in-flight text. The fix planned is to checkpoint a streaming row every few seconds and mark stale ones partial on startup.

06 / numbers

Everything runs twice.

The integration suite is run against PostgreSQL and against SQLite, from the same files. CI does it on every push: one job with Postgres 16 and Redis 7, a second with no services at all, and a third that packs the npm tarball and smoke-tests it.

The end-to-end script is hand-rolled bash rather than a test runner. It builds the gateway, boots it twice — single-user on one port with a temporary data directory, server mode on another against Postgres and Redis — and runs a shared block against both: health and mode, the OpenAPI document, auth failures, the SSE event order, forks, stats, doctor, backup and browser sign-in. That shared block running once per mode is where the number comes from. CI does not run it, because it needs a real Ollama.

The OpenAPI 3.1 document is not written by hand either. A contract test asserts that real responses match it and that every route Fastify registers is documented, by collecting them from a route hook at startup.

07 / decisions

What I chose, and what it cost.

Two backends, one interface

SQLite means a new user runs one command and has a working assistant — no Docker, no database. Postgres means a shared one. The cost is that every feature has to be expressed through a storage port, and the whole integration suite runs twice.

Admission control in-process, in both modes

A distributed limiter would be correct for many servers. There is one GPU, so the honest unit is the process that owns it.

A pessimistic token counter, behind an interface

Three characters per token, deliberately low so the context window is under-filled rather than over. The provider's real count is stored next to the estimate so the estimator can be calibrated from data later, and the response says which number the client got.

Request ids generated server-side

Never trust a client-supplied id. Echoed in every error body and in the response header — set by hand on streaming replies, because a hijacked response skips Fastify's normal hook.

The CLI withholds a key from the wrong gateway

If the base URL points somewhere other than the saved profile and no key was given for it, the saved key is deliberately not sent. Zero-config local pickup reads a credentials file only if the current user owns it and nobody else can read it: a key others can read is not a secret.

A competitor researched, and the conclusion written down

LiteLLM already does gateway features — rate limits, budgets, key management. So the roadmap records that server mode must not be sold on those, and that LiteLLM should instead be considered as one adapter behind the provider interface.

08 / next

What I'd do next.
