01 / what it is

Practice that never waits for a server.

99ile helps students prepare for CAT, India's entrance exam for the IIMs. It plans each day around the time the student actually has, explains why every wrong option was tempting, and keeps bringing their own mistakes back until they stop happening.

The interesting part for an engineer is the constraint I set on day one: everything works as a guest, offline, on one device. Sync, sign-in and AI are additions, never a gate in front of practice. That single rule decided the architecture — practice content ships with the site instead of living in the database, the browser owns the state, and the server's only real job is to order writes so that two of a student's devices agree.

VARC and DILR are live. Quant lands January 2027. Every service runs on a free plan.

  1. No sign-up to start. Everything works as a guest, offline, on one device.
  2. Code counts, AI explains. Scores, schedules and answer checks come from tested code. AI is used only where the answer differs per student, and practice never waits for it.
  3. Original content, checked by tests. Every answer key is tested before it ships. DILR answers are computed by a solver.
  4. Fast on a cheap phone on 4G. The first download has a budget — 155 KB gzipped — and CI fails the build if it is exceeded.
  5. Free to run. Every service is on a free plan.

02 / architecture

The browser owns the state. The server orders the writes.

The browser only ever talks to its own origin: a Cloudflare Pages function forwards /api/v1/* to the Go API with a shared secret. So there is no CORS, the device cookie stays first-party, and the API refuses anything that did not come through the proxy. Point at a box to follow what it touches.

03 / data model

Four tables carry the sync.

Postgres 17, no ORM, goose migrations embedded in the binary. One schema per area and never public; two roles, where the API's role cannot run DDL and the read-only role is denied every secret hash and the record payloads. A migration may only add, because the old server keeps serving while the new schema rolls out.

Four more schemas sit beside these: audit (append-only, IPs stored as an HMAC with a yearly key so they cannot be tracked across years), access (roles and grants, hung off the account table rather than the device table so a stolen cookie can never be an admin), notify (the reminder queue, claimed with SKIP LOCKED — no Redis, no broker) and ai.

04 / the bug that mattered

A sequence hands out numbers before the transaction commits.

The sync cursor is a server-assigned revision number, not a timestamp — phone clocks are wrong, sequences are not. But a Postgres sequence gives out a number the moment it is asked, not when the work commits. Two of a student's devices pushing at once can therefore commit out of order, and a third device can step over a row forever.

Device C's cursor passed 10 before row 10 existed. It will never ask for it again — and nothing reports an error.

The lock is per identity, so two different students never wait for each other — and a pull takes no lock at all.

The fix is the first statement inside the push transaction:

err := pgx.BeginFunc(r.Context(), s.db, func(tx pgx.Tx) error {
    var head struct{ rev, count, bytes int64 }
    if err := tx.QueryRow(r.Context(),
        `select rev, record_count, data_bytes from sync.heads
          where identity_id = $1 for update`,
        d.IdentityID).Scan(&head.rev, &head.count, &head.bytes); err != nil {
        return fmt.Errorf("lock head: %w", err)
    }
    // …read and lock the touched rows, classify each change, write
})

The table's own comment says it in one line: one row per identity. Every push locks it first, so one identity's pushes run in turn and a pull never skips a row.

Beyond the ordering, nothing is ever overwritten blind. Every change names the revision it was based on; if the stored row has moved on, the server returns it as stale with its current copy and the browser merges. A change that is byte-identical to what is stored is reported as applied without burning a new revision, which makes a retried push free. Rejections are per row, never per push, and deletions are always allowed so a student at the record cap can still make room.

Proven by a 40-seed property test that drives two devices through random interleavings and asserts they converge without losing an attempt, plus Go integration tests running concurrent pushes against a real Postgres with -race.

05 / numbers

Ten thousand students, then measured.

A separate database seeded with 10,000 synthetic students — created the way sign-up creates them — then an evening peak replayed through the real API with a 1 ms proxy lag and a single CPU. The footprint came out at 10.7 million records and 5.5 GB: 563 KB per student, 538 bytes per record. The JSON the browsers sent is only 1.7 GB; the rest is row and index overhead.

250 sessions a second is about twenty times the expected peak for 10,000 students. The gain came from replacing per-row round trips with two set-based statements using unnest(…) with ordinality — which is also why there is no ORM.

06 / what it does

Built for one exam, properly.

Practice

  • 55 reading sets across 9 genres, every wrong option carrying a note on why it tempted you
  • 80 verbal paragraphs, each yielding four question types
  • 59 logic and data sets, answers recomputed by a solver rather than typed in
  • Drills, sectionals, speed tests and a replay mode
  • Mistakes come back until they stop happening

Planning

  • A plan built around the hours the student says they have, not a fixed calendar
  • Today, progress, history, error log, word list, journal, week review

Accounts and sync

  • Three levels, in order of what you give up: a backup file, anonymous sync, a Google account
  • Device linking by QR or an 8-character code; a 16-character recovery code
  • Device list, remove a device, export everything, delete everything
  • Sign-in uses PKCE and never creates a second session type — it repoints the device

Reminders and AI

  • Study reminders by push or email, in the student's own time zone, with quiet hours
  • Feedback on the student's own 25-word summary, quoting their words, never rewriting
  • The smallest edit that makes all four checks pass, with the edit distance capped in code
  • Paste any article and get a CAT-style set: one model writes, code checks, a second model answers blind

07 / decisions

What I chose, and what it cost.

Server revisions, not timestamps

Device clocks are wrong, sometimes by hours. A sequence gives total order for free. The device's own hybrid clock still rides on each record, but only as a merge tiebreak — never as the cursor.

Compare-and-set, not last-write-wins

Last-write-wins is one column and no round trips, and it silently eats a student's answers when two devices are open. Naming the base revision makes the conflict visible so the browser can merge it, and every merge rule is commutative by construction.

A lock per identity, not a global one

Serialising all pushes would have been simpler and would have scaled to roughly one student at a time. Locking the head row scopes the contention to exactly the writes that must be ordered.

Content in the repository, not the database

Practice content is JSON checked by tests on every change. A content fix is a pull request with a test, the site works offline, and the database stays small. The cost: adding content needs a deploy.

localStorage, not IndexedDB

One string holds the whole app state. Simple, synchronous, and fine up to a few megabytes. The move to IndexedDB is already specced for when a serious student's history outgrows it — the sync ledger already knows which records changed.

AI only where the answer differs per student

"Explain my mistake" was built and then deleted: its answer is the same for everyone who picks that option, so it belongs in the content as a tested note, not in a live model call.

Three things were tried and reverted, which I think is worth recording: a login cache, because it broke a test that matters — a student suspended in the database must be refused at once; answering empty pulls from memory, because it showed no measured gain; and gzip in the API, because Cloudflare already compresses.

08 / next

What I'd do next.

Quant from January to March 2027. IndexedDB instead of one localStorage string, writing only the records that changed. Partition sync.records by hash of the identity past about 50 million rows. And an end-to-end browser suite — today those checks are manual, listed per branch.
